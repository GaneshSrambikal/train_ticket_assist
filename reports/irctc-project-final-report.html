IRCTC Booking Automation
Final Decision Report

15 October 2026  |  Personal General & Tatkal booking assistant
Assessment based on project tests, supplied diagnostic evidence and official documentation.

Decision: discontinue the current booking-automation project. Do not deploy the Playwright booking flow or proceed with the proposed extension as a workaround. Retain useful local preparation and validation components. Continue actual bookings through IRCTC’s normal user interface.

Why we are stopping

1. The intended use conflicts with published service terms

IRCTC’s general user terms explicitly state:

“Use of automation software and/or Scripting Software is strictly prohibited.”

This appears in the General section on PDF page 7. The surrounding terms describe account and ticket consequences for specified misuse. This is a service-policy reason to stop, independent of whether the code can technically be made to work. [1 — official terms]

2. The tested browser workflow receives an access denial

Manual booking reached review in normal Chrome and Incognito, according to the user’s tests. The same manual flow in Playwright-launched Chrome failed. Diagnostics recorded HTTP 403 responses immediately before the error page. The supplied response names the protected endpoint and an Akamai error reference. See the evidence on page 2.

3. Rebuilding as an extension has no demonstrated solution

An extension would run in the normal browser, but its scripts still change the page. Chrome’s isolated script environment is not a promise that those changes are invisible. No successful extension test or IRCTC permission was established. Changing the delivery method does not resolve the published restriction. [3 — Chrome documentation]

Project rationale: further investment would depend on an unverified technical workaround without an established permitted deployment path. The useful prototype work can be retained without pursuing automated booking.

Evidence and limits

What the tests established

The following findings distinguish observed failures from possible explanations.

Normal Chrome and Incognito reached review during manual use.The user has a working manual booking route.
Manual use of Playwright-launched Chrome still reached the error page.Autofill and automatic Continue clicks were not necessary to reproduce the failure.
Both browser versions were 155.0.8059.40.A version mismatch does not explain these runs. Launch and session settings can still differ.

Access-denial evidence

The user supplied an HTML response titled Access Denied, identifying:

Endpoint: /eticketing/protected/mapps1/allLapAvlFareEnq/Y
Reference: 18.b7f43017.1792064155.10caa9e7
Error host: errors.edgesuite.net

The error host is associated with Akamai infrastructure. The response supports an edge access-denial finding, but does not reveal the exact rule. [4 — Akamai infrastructure]

What we cannot claim

  • We cannot prove that a specific automation-detection rule caused this denial. The site operator’s security logs are needed.
  • We cannot claim that every browser extension would fail, or that one would solve the issue. No extension implementation was tested.
  • The diagnostic report omits request URLs and bodies. It cannot establish that both rejected request IDs used the same endpoint.
  • The manual and automated-browser comparisons were user-run tests, not a simultaneous controlled experiment.

Evidence basis: supplied browser-version screenshot, error-page screenshots, pasted diagnostic JSONL and Access Denied response. These are project observations, not an IRCTC certification or official root-cause finding. Longer waits do not reverse the recorded 403 refusals.

Closeout and references

Recommended next steps

  1. Close the automated-booking scope. Preserve the prototype and findings as research artifacts; do not present them as a reliable booking product.
  2. Use the normal booking interface. Use IRCTC’s built-in passenger Master List where available. Keep reminders, local validation and preparation tools separate from website control.
  3. Seek clarification only if needed. Submit the error reference, endpoint, failure time/timezone and browser comparison through IRCTC eQuery [5]. Disclose that the failing manual test used Playwright-launched Chrome.
  4. Reconsider only with new evidence. An approved integration scope and successful end-to-end validation would be needed to justify restarting. A successful page load or form fill is insufficient.

Akamai’s customer-side error translator can retrieve failure information and firewall details. Its documented log window is only 6 or 24 hours, depending on conditions; the old reference may no longer be retrievable. Support investigation does not guarantee permission or an exemption. [2]
